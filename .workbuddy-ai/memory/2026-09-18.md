# 2026-09-18 — Modul MBKM (end-to-end)

## Yang dikerjakan
Membangun **Modul MBKM** lengkap di `backend/modules/MBKM/` + UI di `frontend/src/pages/mbkm/`,
terintegrasi ke sistem akademik yang sudah ada. Selesai sampai UI + verifikasi.

## Backend — `backend/modules/MBKM/` (84 berkas PHP, ~10.800 baris)
- **Enums (17)**: ProgramStatus, ApplicationStatus, ParticipantStatus, DocumentStatus,
  LearningAgreementStatus, ActivityPlanStatus, LogbookStatus, MbkmAttendanceStatus,

- **Migrations 3**: `..._create_mbkm_master_tables`, `..._create_mbkm_workflow_tables`,
  `..._create_notifications_table` (tabel notifikasi Laravel native, karena modul ini yang pertama butuh).

## Keputusan arsitektur penting
- **KHS/transkrip TIDAK disimpan** — `StudentPortalService::getStudentKHS()` menurunkannya dari
  `student_enrollments` → `student_enrollment_items` → `academic_classes` → `GradeCalculationService`.
  Jadi MBKM **mendorong** hasil ke tabel akademik lewat `MbkmAcademicIntegrationService`, tidak
  membuat tabel KHS sendiri. IPK tidak dihitung ulang.
- **Skala nilai** pakai `GradeScale`/`GradeScaleItem` yang ada + `GradeCalculationService::convertScoreToGrade()`.
  Tidak ada A=4 hardcoded.
- **Dokumen**: modul ini memiliki satu tabel `mbkm_documents` (karena belum ada document management).
  Dokumen pendaftaran menempel ke `application`, dokumen pelaksanaan ke `participant`.
  `MbkmParticipant::hasDocumentCategory()` + `allDocuments()` mengecek keduanya tanpa memindah baris.
- **Kuota**: `DB::transaction` + `MbkmProgram::lockForUpdate()`.
- **Eligibility explainable**: `checks[]` (`code/label/passed/message/type`) + `reasons[]`.
- **Otorisasi**: `MbkmAuthorization` trait — `mayWriteParticipant` (owner/supervisor/manager) vs
  `mayManageParticipant` (manager/supervisor, peserta dikecualikan). `student_id`/`participant_id`
  dari request tidak pernah dipercaya; selalu di-resolve dari `auth()->user()`.
- **PDDikti/Neo Feeder**: tidak ada di repo → tidak dibuat endpoint/sync palsu. Ada guard yang menolak.

## Ronde 3 — audit otorisasi menyeluruh (sistematis)

Ronde 2 hanya menemukan bug karena kebetulan. Ronde 3 memakai **skrip audit** yang
membandingkan `Routes/api.php` dengan isi method setiap controller, lalu menandai endpoint
yang **tidak punya cek otorisasi di method DAN tidak punya middleware `permission:`** —
kombinasi itu berarti terbuka untuk siapa pun yang sudah login.

Skrip audit ada di memori ini (lihat bagian "Cara mengaudit") — pakai lagi kalau menambah route.

### Temuan 1 (KEAMANAN, P1) — kebocoran dokumen lintas mahasiswa
`GET /mbkm/documents` (`MbkmDocumentController::index`) **tanpa cek otorisasi dan tanpa
middleware**. Siapa pun yang login bisa menarik sampai 200 dokumen **seluruh institusi**
(KTM, CV, sertifikat semua mahasiswa) beserta `file_path`. Ini tepat melanggar
"Must prevent: cross-student data access".

`store()` juga hanya membatasi **mahasiswa**; pengguna non-mahasiswa mana pun (mis. dosen tanpa
permission MBKM) bisa mengunggah berkas ke entitas MBKM mana pun.

Perbaikan:
- Helper baru di `MbkmAuthorization`: `visibleStudentIds()` (null = tanpa batas untuk
  module manager, `[]` = tidak boleh lihat apa pun), `maySeeStudent()`.
- `index()` menerapkan scope SEBELUM filter apa pun; mahasiswa → dokumen miliknya,
  dosen → peserta bimbingannya, kaprodi → prodinya, manager → semua, lainnya → kosong.
- `store()` untuk non-mahasiswa lewat `mayUploadToEntity()`.
- `verify()`/`destroy()` lewat `mayTouchDocument()`.

### Temuan 2 (KEAMANAN) — 9 endpoint administratif tanpa scope peserta
`participants/{id}/start|finalize-score|placement|supervisors|completion/verify|certificate|learning-agreement/reopen`
dan `participants/{id}` (PUT) hanya mengandalkan middleware `permission:mbkm.participants.manage|…`.
Tidak ada cek bahwa peserta itu **dalam wewenang** pemanggil.

Dengan seed default ini belum bisa dieksploitasi (hanya `super_admin` yang memegang permission
staf MBKM — `admin_akademik` dapat permission **per grup**, dan grup `mbkm` tidak termasuk).
Tapi begitu dibuat role kaprodi dengan `mbkm.manage_study_program` + `mbkm.participants.manage`,
admin prodi A bisa mengubah peserta prodi B. Ini melanggar "Must prevent: cross-prodi edits".

Perbaikan: `mayManageParticipant()` ditambah cabang prodi (`managesParticipantStudyProgram()`),
lalu dipasang di 9 endpoint tersebut. Untuk `attachCertificate`, cek dipasang **sebelum**
`$file->store()` supaya pemanggil tak berwenang tidak sempat menulis ke disk.

### Temuan 3 (BUG di kode saya sendiri) — urutan cabang `visibleStudentIds()`
Kaprodi itu **juga** seorang `dosen`, jadi `isMbkmLecturerOnly()` bernilai true untuk mereka.
Versi pertama saya memeriksa cabang dosen **sebelum** cabang prodi → kaprodi hanya melihat
peserta yang mereka bimbing sendiri, bukan seluruh prodinya. Bukan kebocoran, tapi salah.
Perbaikan: **cabang prodi diperiksa lebih dulu**, baru cabang dosen.

### Cara mengaudit (pakai lagi kalau menambah route)
Skrip Python yang dipakai: parse `Route::(get|post|…)\('uri',\s*\[Ctrl::class,\s*'method'\]\)(.*?)`
lalu ambil `middleware\('…'\)` dari ekor; parse tiap controller jadi peta method→body dengan
penghitung kurung; tandai bila `not has_auth and not has_permission`. Regex `AUTH` harus
mencakup `visibleStudentIds|maySeeStudent|mayTouchDocument|mayUploadToEntity` **dan**
`\$request->user\(\)` (endpoint notifikasi memakai `$request->user()` sebagai scope, bukan
helper — tanpa itu akan salah dilaporkan terbuka).

### Verifikasi ronde 3
- `php artisan test --filter=MbkmWorkflowTest` → **10 passed (164 assertions)**
- Audit ulang: **111 route, 0 endpoint terbuka**
- `php artisan test` → lihat hasil di bawah

### Tes baru ronde 3
- `test_document_listing_is_scoped_to_the_viewer` — mahasiswa hanya lihat dokumennya;
  dosen non-pembimbing lihat kosong; manager lihat semua; mahasiswa 403 saat verify dokumen orang lain.
- `test_study_program_scoped_admin_cannot_touch_other_programs_participants` — kaprodi prodi lain
  403 pada `start` + dokumen tak terlihat; kaprodi prodi yang sama 200 + dokumen terlihat.

**Jebakan:** permission di repo ini **hanya lewat role** — tidak ada pivot user↔permission.
`User::givePermissionTo()` tidak ada. Untuk tes, buat `Role` + `$role->permissions()->sync([...])`
lalu `$user->assignRole($role)`.

## Ronde 4 — Audit State Machine & Konektivitas Frontend (2026-09-18, lanjutan)

### Temuan 1 — State machine tidak seragam
Hanya `ProgramStatus` yang punya `transitions()`/`canTransitionTo()`. `LearningAgreementStatus`
dan `RecognitionStatus` memakai inline `match` map + `LOCKED => []` (aman, eksplisit).
`LogbookStatus` **tidak punya peta transisi sama sekali** — hanya precondition ad-hoc di service.
Ini yang membuka dua bug di bawah.

### Temuan 2 (BUG) — logbook final bisa dibuka kembali
`MbkmLogbookService::review()` tidak memeriksa `isFinalized()`. Pembimbing bisa memindahkan
logbook `approved` (terkunci) → `revision_required`, yang otomatis **membuka kunci edit bagi
mahasiswa**. Melanggar "data final tidak dapat diubah lewat endpoint normal".
Perbaikan dua lapis: tolak bila `$log->isFinalized()`; tolak bila status asal bukan `submitted`
(sebelumnya transisi dari `draft` pun lolos).

### Temuan 3 (BUG) — nilai akhir bisa dibekukan dari penilaian belum lengkap
`MbkmParticipantService::finalizeScore()` menghitung `is_complete` dari
`MbkmAssessmentService::computeFinalScore()` tapi **hasilnya diabaikan**. Penilaian 2 dari 5
komponen bisa difinalisasi → nilai terlalu rendah **permanen** langsung mengalir ke KHS/transkrip.
Perbaikan: tolak bila `is_complete` false, pesan menyebut komponen yang belum dinilai;
tambah parameter `force` (body `{ "force": true }`) sebagai jalan keluar sadar-risiko.
Frontend: `AlertTriangle` saat `is_complete` false + dialog konfirmasi berubah + kirim `force`.

### Temuan 4 (BUG PALING HALUS) — panel "Komponen & Bobot" selalu kosong
Backend mengirim `final_score.breakdown[]` dengan `component_name` / `assessors`.
Frontend membaca `finalScore.components`, `c.code`, `c.name`, `c.is_scored` — **tidak ada
satupun yang dikirim**. Karena `finalScore` ditipekan `ref<any>`, TypeScript tidak bisa
menangkapnya: panelnya **selalu kosong tanpa error apa pun**.

**Tidak akan pernah tertangkap oleh tes backend** — endpoint tetap 200 dengan struktur benar.
Penangkalnya: hindari `ref<any>` untuk payload berstruktur tetap, definisikan interface eksplisit.

Diperbaiki di 3 halaman:
- `participants/Show.vue` — `breakdown`, `c.component_id`, `c.component_name`, `c.assessors > 0` (3 tempat)
- `my/Index.vue` — idem (3 tempat)
- `applications/Index.vue` — `selection.score` (bukan `weighted_score`), `selection.breakdown`,
  `c.criteria_name` (bukan `c.name`), `c.reviewers > 0` (bukan `c.is_scored`)

Tipe `MbkmFinalScore` diganti dari `any` → interface eksplisit + `MbkmFinalScoreBreakdown`.

### Temuan 5 — kosakata `assessor_type` ganda (dituntaskan)
`ASSESSOR_TYPE_LABELS` frontend memuat `final_report`/`presentation`/`project` — **ditolak
backend 422** — dan tidak memuat `co_supervisor`/`committee`. Sementara
`components.*.assessor_type` divalidasi sebagai teks bebas (`max:40`) padahal penilaian memakai
daftar `in:` hardcoded → nilai tak sah bisa menyelinap ke record penilaian.
Perbaikan: enum `AssessorType` (**siapa** menilai) + `AssessmentComponentType` (**apa** diukur)
sebagai sumber kebenaran tunggal, dipakai di kedua endpoint, peta label frontend disamakan.

## Ronde 5 — Mass Assignment, State Machine Peserta & Scope Listing (2026-09-18, lanjutan)

Fokus: area yang belum pernah diaudit — mass assignment, state machine `ParticipantStatus`,
dan kelengkapan scope endpoint listing.

### Mass assignment — BERSIH
Tidak ada `->all()` / `->except()` / `->only()` / `->merge()` di seluruh modul. Semua
`create()`/`update()` pakai array hasil `validate()` dengan field eksplisit + `$fillable`.

### BUG 1 (integritas) — `PUT participants/{id}` pintu belakang state machine
`MbkmParticipantController::update()` menerima `status` dan menulis **langsung ke kolom** hanya
dengan penjagaan `in:` terhadap daftar enum. Bisa lompat `assigned → completed` melewati
penempatan, LA, logbook, presensi, penilaian, verifikasi penyelesaian. Peserta jadi `completed`
tanpa satu pun record penyelesaian, **tetap memakan slot kuota** (`occupyingQuota()` mencakup
`completed`), dan **tanpa jejak di `mbkm_status_histories`** karena `update()` melewati history
service. Peserta terminal juga bisa dihidupkan kembali jadi `ongoing`.

Perbaikan dua lapis:
- `ParticipantStatus` dapat `transitions()`, `canTransitionTo()`, `isTerminal()`, `workflowOnly()`.
  `workflowOnly()` = `[ongoing, completed, withdrawn, terminated]`.
  **Satu-satunya status yang boleh diubah lewat `PUT participants/{id}` adalah `failed`**
  (tidak punya endpoint sendiri).
- `MbkmParticipantService::updateAdministrative()` — validasi transisi, tolak `workflowOnly()`
  dengan pesan yang menunjuk alur resminya, dan **selalu tulis riwayat** (`participant.status_changed`).

### BUG 2 (kebocoran) — `indexWithdrawals()` & `indexExtensions()` hanya scope mahasiswa
```php
if ($this->isMbkmStudent($request)) { ... }   // tidak ada cabang dosen, tidak ada default
```
Route tanpa middleware → **setiap pengguna terautentikasi** (termasuk dosen non-pembimbing)
membaca seluruh permohonan pengunduran diri & perpanjangan se-institusi. Ironinya `index()`
(penyelesaian) di controller yang sama **sudah** punya cabang dosen. Perbaikan: pakai
`visibleStudentIds()` (pola sama dengan `MbkmDocumentController` ronde 3).

### BUG 3 (otorisasi) — keputusan permohonan tanpa scope & bisa diulang
`decideWithdrawal()` / `decideExtension()` hanya mengandalkan middleware route, tanpa cek
(a) peserta dalam wewenang pemanggil, (b) permohonan masih `pending`. Akibatnya admin prodi A
bisa memutuskan peserta prodi B, dan keputusan bisa ditimpa (`rejected → approved`) — tiap
keputusan ulang menulis ulang status peserta + menambah baris history.
Perbaikan: `mayManageParticipant()` + `if ($current !== 'pending') → 422`.

### BUG 4 (kebocoran) — `GET /mbkm/history` terbuka untuk dosen
Route diberi `permission:mbkm.manage|mbkm.participants.view`. Role **`dosen` memegang
`mbkm.participants.view`**, dan feed itu **tidak di-scope** → dosen bisa membaca seluruh riwayat
transisi status semua mahasiswa. Perbaikan: persempit ke `mbkm.manage`. Riwayat per peserta
tetap ada & ter-scope di `GET participants/{id}/history`. Endpoint ini tidak dipakai UI
(`getHistory()` di service frontend tidak pernah dipanggil).

### BUG 5 (validasi) — `exists:` bukan bukti kepemilikan
`storeWithdrawal()` validasi `document_id` hanya `exists:mbkm_documents,id` → mahasiswa bisa
melampirkan **dokumen mahasiswa lain**. Perbaikan: cek
`$participant->documents()->whereKey($id)->exists()` → 422.

### ⚠️ KOREKSI: skrip audit saya sendiri punya false-negative
Regex `AUTH` versi lama memuat `\$request->user\(\)`. Itu **bukan bukti otorisasi** — method yang
hanya mengoper user ke service (`$this->service->decide($x, $request->user())`) lolos sebagai
"aman". Inilah yang menyembunyikan BUG 3.
Perbaikan skrip: dua keranjang — `!! OPEN` (tanpa permission, tanpa AUTH_CALLS, tanpa
`$request->user()`) dan `?? REVIEW` (hanya `$request->user()`). Hasil: **111 route, 0 OPEN,
3 REVIEW** (ketiganya endpoint notifikasi, self-scoped lewat `$request->user()->notifications()`).
Skrip lengkap: `/tmp/mbkm_route_audit.py`.

**Batas kemampuan skrip — penting.** Skrip hanya membuktikan **ADA** cek, bukan bahwa cek itu
**LENGKAP**. 4 dari 5 temuan ronde 5 lolos audit otomatis:
| Temuan | Kenapa lolos |
|---|---|
| listing tidak lengkap | memuat `isMbkmStudent` + `currentStudent` → tampak seperti otorisasi |
| keputusan tanpa scope | punya `permission:` middleware |
| `history` terlalu longgar | punya `permission:` middleware |
| state machine | punya `permission:` middleware |

Tiga pemeriksaan manual yang wajib menyertai skrip:
1. **Bandingkan method listing dengan listing sejenis di controller yang sama.** Ada yang punya
   cabang role dan ada yang tidak → bug.
2. **Untuk tiap route ber-`permission:`, tanya role mana yang memegangnya** dan apakah mereka
   semua pantas melihat data itu **tanpa scope**. Permission "view" milik dosen + endpoint tanpa
   scope = kebocoran.
3. **Untuk tiap endpoint tulis, tanya apakah record sasaran diperiksa dalam wewenang pemanggil.**
   Middleware hanya membuktikan "staf".

### Koreksi lain terhadap laporan sendiri
Saat investigasi BUG 3 saya sempat menyimpulkan `decideWithdrawal()` "tanpa otorisasi sama
sekali". **Tidak akurat** — route-nya punya middleware `permission:mbkm.participants.manage|mbkm.manage`.
Kesimpulan itu muncul karena `grep -B 3` memotong baris `->middleware(...)` di baris berikutnya.

## Ronde 6 — Integritas Level Database & Race Condition (2026-09-18, lanjutan)

Fokus: constraint DB (apakah "mencegah duplikat" ditopang unique index atau hanya cek aplikasi)
dan race condition pada pola baca-lalu-tulis.

### Constraint DB — sebagian besar benar
Unique index sudah ada untuk: `participants(program_id,student_id)` + `participant_number`,
`selection_scores`, `placements(participant_id)`, `learning_agreements(participant_id)`,
`completions(participant_id)`, `attendances(participant_id,attendance_date)`,
`assessment_components(program_id,code)`, `assessments(participant_id,component_id,assessor_type,assessor_user_id)`
(`assessor_user_id` selalu terisi → aman).

### BUG (integritas) — race condition pada rekognisi
`assertNoDuplicate()` (`exists()`) dan `assertCreditCeiling()` (`sum()`) keduanya
**baca-lalu-tulis tanpa lock**. Diperburuk: `create()` dalam transaksi tapi **tanpa lock**;
`update()` **tidak punya transaksi sama sekali**; `transition()` memvalidasi state machine
**di luar** transaksi.

Akibat dua request bersamaan: (a) **dua rekognisi untuk MK yang sama** → MK dihitung dua kali di
KHS (tiap rekognisi yang disetujui menulis satu `student_enrollment_item`); (b) **batas SKS
terlewati** — keduanya membaca `$existing` yang sama; (c) **satu rekognisi disetujui dua kali**
→ SKS yang sama masuk dua kali ke pipeline akademik.

Perbaikan:
- Helper `lockParticipant()` — row lock pada **baris peserta** (selalu ada → `lockForUpdate()`
  deterministik). Mengunci baris rekognisi tidak mungkin (belum ada); gap lock pada
  `mbkm_recognitions` bergantung engine + isolation level.
- `create()` → lock di awal transaksi. `update()` → **kini dibungkus `DB::transaction`** + lock.
- `transition()` → setelah lock, `refresh()` + **validasi ulang transisi**; model basi ditolak
  dengan pesan "muat ulang data".

### 3 temuan yang SENGAJA TIDAK diubah (dilaporkan apa adanya)
1. **`mbkm_applications` tanpa unique `(program_id, student_id)`** — unique biasa akan
   **mematahkan daftar-ulang yang sah** (mahasiswa boleh mendaftar lagi setelah ditolak; lihat
   `ApplicationStatus::activeStatuses()`). Butuh *partial unique index* → tidak didukung MySQL.
   `create()` sudah pakai `lockForUpdate()` pada query cek duplikat → di MySQL/InnoDB gap lock
   pada index itu **memang** menyerialkan, tapi implisit + bergantung engine, dan **tidak
   teruji** karena SQLite mengabaikan `lockForUpdate()`.
2. **`mbkm_supervisors` unique `(participant_id, role, lecturer_id)` dengan `lecturer_id` nullable**
   → NULL tidak dianggap sama di unique index → pembimbing lapangan eksternal ganda bisa dibuat.
   Perbaikan juga butuh partial index.
3. **Satu penilai bisa memberi dua nilai untuk satu komponen** — unique index memuat
   `assessor_type`, dan `store()` menerima `assessor_type` apa pun yang valid (bukan hanya milik
   komponen). `computeFinalScore` merata-ratakan keduanya → **suara penilai itu berbobot ganda**.
   Tidak diubah karena modal "Input Penilaian" di UI memang menawarkan dropdown `assessor_type`.
   **Perlu keputusan produk.**

Catatan kecil: `MbkmAssessmentService::record()` pakai `updateOrCreate` non-atomik → dua submit
bersamaan bisa menabrak unique index dan memberi 500 (bukan korupsi data).

### Tes baru ronde 6

**Batas kejujuran:** race sesungguhnya **tidak bisa direproduksi** di SQLite in-memory (yang

## Ronde 7 — Operasi Hapus & Pembekuan Nilai (2026-09-18, lanjutan)

Kelas bug yang sama seperti `review()`/`finalizeScore()` (ronde 4), tapi pada operasi `DELETE`.

### Yang sudah benar
`DELETE logbooks` (`isFinalized`), `DELETE recognitions` (`isLocked`), `DELETE programs`
(menolak bila ada peserta), `DELETE program-types`, `DELETE partners` (menolak bila dipakai
penempatan), `DELETE documents` (`mayTouchDocument`), `DELETE supervisors`
(`mayManageParticipant`). Siklus hidup logbook **lengkap**: `update`/`submit`/`review`/`destroy`
semuanya cek `isFinalized()`.

### BUG 1 — mahasiswa bisa menghapus nilai yang dicatat pembimbingnya
`MbkmAssessmentController::destroy()` hanya memeriksa **kepemilikan peserta**
(`mayWriteParticipant` — yang **memasukkan mahasiswa**), bukan kepemilikan **baris**.
Padahal `store()` sudah membatasi mahasiswa: `$validated['assessor_type'] = 'self'`.
`destroy()` tidak mencerminkan aturan itu → mahasiswa bisa menghapus baris penilaian milik
**pembimbing** atau **mitra** untuk komponen apa pun. Karena `computeFinalScore()` merata-ratakan
baris per komponen, menghapus nilai rendah **menaikkan rata-rata baris tersisa** → nilai akhir dan
huruf mutu di KHS naik.
Perbaikan: mahasiswa hanya boleh menghapus baris `self` miliknya sendiri
(`assessor_type === 'self'` **dan** `assessor_user_id === user`); non-mahasiswa lewat
`mayManageParticipant`.

### BUG 2 — komponen penilaian tidak terkunci setelah nilai akhir dibekukan
`MbkmAssessmentService::record()` dan `destroy()` **tidak memeriksa `score_finalized_at`**.
Setelah `finalizeScore()` membekukan nilai, komponen masih bisa ditambah/ditimpa/dihapus →
`final_score` tidak lagi sama dengan komponen yang diklaim merangkumnya.
Perbaikan: keduanya menolak bila `score_finalized_at !== null` → 422.

### Temuan yang SENGAJA TIDAK diubah (perlu keputusan produk)
**Presensi MBKM self-reported tanpa langkah verifikasi.** `store`/`batch` memakai
`mayWriteParticipant` → mahasiswa mencatat presensi sendiri dengan status & tanggal apa pun
(termasuk `present`); `destroy` juga miliknya → baris `absent` bisa dihapus. Karena
`attendance_percentage = (present + late) / total`, menghapus baris `absent` **menurunkan `$total`
tanpa mengubah `$attended`** → persentase naik → `min_attendance_percentage` (prasyarat
penyelesaian) terlewati.
**Mengencangkan `destroy` saja tidak menutup lubang** — `store` sudah mengizinkan fabrikasi.
Perbaikan benar butuh kolom `verified_by`/`verified_at` + hanya menghitung baris terverifikasi.

**Stub menyesatkan:** `MbkmAttendanceService::assertParticipantAcceptsAttendance()` berdocblock
*"Guard used by controllers"* tapi isinya hanya `$participant->exists` — **selalu benar** untuk
model yang di-resolve dari route. Tidak menjaga apa pun.

### Dua koreksi terhadap analisis saya sendiri

|---|---|
| "`store()` pakai `mayManageParticipant`, `destroy()` pakai `mayWriteParticipant` — asimetri permission" | **Keduanya** `mayWriteParticipant`. Asimetrinya di **aturan peran**, bukan permission. |
| "Mahasiswa bisa memalsukan `assessor_type`" | **Tidak.** `store()` sudah memaksa `assessor_type = 'self'` untuk mahasiswa. |

**Pelajaran:** baca method lengkap sebelum menyimpulkan. Dua kali di ronde ini saya menyimpulkan
dari potongan kode dan dua kali salah.

## Ronde 8 — Sweep pola "scoping berbasis cabang peran"

Ronde 5 menemukan satu kebocoran pada `indexWithdrawals()`. Ronde 8 memeriksa apakah itu
kecelakaan atau **pola**. Jawabannya: pola — dan ini temuan terpenting sejauh ini karena satu
akar masalah menjelaskan hampir semua kebocoran listing di modul.

### Pola akar masalah (WAJIB DIINGAT)

Hampir semua listing di modul MBKM men-scope dengan cabang peran:

```php
if ($this->isMbkmStudent($request)) {
    $query->where('student_id', $this->currentStudent($request)?->id);
} elseif ($this->isMbkmLecturerOnly($request)) {
    $query->whereHas('supervisors', fn ($q) => $q->where('lecturer_id', $lecturerId));
}
```

Konstruksi ini **fails open** untuk setiap peran yang tidak disebutkan:

| Peran | `isMbkmStudent` | `isMbkmLecturerOnly` | Akibat |
|---|---|---|---|
| `mahasiswa` | ✅ | ✗ | ter-scope (benar) |
| `dosen` biasa | ✗ | ✅ | ter-scope (benar) |
| `admin_akademik` | ✗ | ✗ | **tanpa scope apa pun** |
| Kaprodi | ✗ | ✗ | **tanpa scope apa pun** |

**Yang paling mudah terlewat:** kaprodi juga seorang `dosen` — jadi cabang "dosen" pun tidak
menangkap mereka (`isMbkmLecturerOnly()` bernilai `false` karena mereka memegang
`mbkm.manage_study_program`... sebenarnya karena `isMbkmLecturerOnly` = `hasRole('dosen') &&
!hasPermissionTo('mbkm.manage')` → true, tapi cabangnya tidak dijalankan karena listing lama
memang tidak punya cabang untuk mereka).

**Perbaikan yang benar bukan menambah cabang ketiga** — itu hanya memindahkan lubangnya. Pakai
`visibleStudentIds()` dengan kontrak: `null` = tak dibatasi, `[]` = **melihat nol baris**
(default-deny), `[id,…]` = terbatas. Urutan cabang penting: `mbkm.manage_study_program` harus
sebelum cabang dosen biasa.

### 5 bug ronde 8

| # | Bug | Sifat |
|---|---|---|
| 1 | `MbkmDashboardController::index()` jatuh ke dashboard admin untuk **semua** peran lain → `admin_akademik` (tanpa permission `mbkm.*`) dilayani statistik institusi | kebocoran |
| 2 | `admin()` tanpa cek manager in-method (hanya middleware) | defense-in-depth |
| 3 | Lima listing tanpa default-deny: `participants`, `recognitions` (**tanpa middleware permission sama sekali**), `logbooks`, `issues`, `applications` | kebocoran |
| 4 | `verify`/`decide`/`score` **tanpa scope per-record** — hanya bertumpu permission module-wide | otorisasi, **laten** |
| 5 | `mayAccessApplication()` menolak kaprodi → daftar menampilkan baris yang detailnya 403 | fungsional |

**Kejujuran soal #4:** **laten**, bukan sedang dapat dieksploitasi. Dari seeder bawaan hanya
`super_admin` yang memegang `mbkm.applications.verify`/`decide`; `admin_akademik` tidak punya
permission `mbkm.*` sama sekali; `dosen` hanya sisi *view*. Tetap diperbaiki karena niat adanya
`mbkm.manage_study_program` jelas (kaprodi memang dimaksudkan memverifikasi prodinya sendiri).

### Perubahan kode

- `MbkmAuthorization` trait: helper generik baru `managesStudentStudyProgram(Request, ?int
  $studentId)`; `managesParticipantStudyProgram()` kini mendelegasikan ke sana (dipakai untuk
  pendaftaran, yang ada **sebelum** penempatan sehingga belum terikat `MbkmParticipant`).
- `MbkmApplicationController`: `mayAccessApplication()` kini = `maySeeStudent()` (scope listing
  dan scope record jadi identik secara definisi); helper baru `mayManageApplication()`; guard
  ditambahkan di `verify()`, `decide()`, `score()` **sebelum** `$request->validate()` sehingga
  payload tidak valid pun menghasilkan 403, bukan 422.
- Enam listing + dua method dashboard: `visibleStudentIds()` / `isMbkmManager()`.
